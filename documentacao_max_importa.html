Documentação Técnica — v4.1.1

Max_Importa

Importador de dados para o sistema MaxManager. Centraliza a importação de Produtos, Clientes/Fornecedores e lançamentos Financeiros via arquivos CSV ou TXT, e a Migração entre Bancos MaxData (banco → banco, na mesma instância SQL), com interface visual MaxData, mapeamento automático de colunas e rastreabilidade completa por logs.

Python 3.11+
CustomTkinter 5.2+
pyodbc 5.3+
SQL Server
ODBC Driver 17
Windows 10/11
MaxManager ERP
01 — Visão Geral

Sobre o Sistema

O Max_Importa é uma aplicação desktop desenvolvida em Python que permite importar grandes volumes de dados para o banco de dados do MaxManager de forma rápida, validada e rastreável.

📦
Produtos
INSERT e UPDATE nas tabelas produto e produto_empresa. Lookup automático de unidade (produtoUn), NCM, CEST, fabricante, grupo, subgrupo e código de barras (codBarras).
👥
Clientes / Fornecedores
INSERT e UPDATE nas tabelas cliente e cliente_empresa. No UPDATE, pode usar CPF/CNPJ como chave alternativa quando cliId não estiver disponível.
💰
Financeiro
INSERT de lançamentos na tabela vendaPgto. Localiza o cliente pelo CPF/CNPJ e exporta em arquivo .txt os registros não encontrados para correção.
🔄
Migração entre Bancos
Copia Clientes, Permissões, Produtos e Financeiro de um banco MaxData para outro da mesma instância SQL, sem arquivo — com tratamento de estoque, duplicados e acerto de estoque automático.
🗂
Logs e Relatórios
Cada importação gera um arquivo .log em tempo real e um relatório .txt de fechamento, salvos na pasta configurada pelo usuário.
02 — Pré-Requisitos

Requisitos do Sistema

Para usar o Max_Importa você precisa apenas dos itens abaixo — o instalador cuida do resto.

  • 🖥
    Sistema Operacional: Windows 10 ou Windows 11 (64 bits)
  • 🗄
    SQL Server com as tabelas do MaxManager já criadas e acessíveis (instância local ou na rede), e um usuário com permissão de leitura/escrita.
  • 🔌
    ODBC Driver 17 for SQL Server — obrigatório para conectar, mas instalado automaticamente pelo instalador quando ausente. Só é preciso baixar manualmente (https://aka.ms/odbc17) se a instalação automática falhar.
  • 🔐
    Permissão de administrador na máquina, apenas no momento da instalação (para instalar o driver ODBC e o Visual C++). O uso do dia a dia não exige administrador.
  • 💾
    Espaço em disco: cerca de 250 MB, considerando o programa, a documentação, os modelos e o banco ZERO compactado.
🛠️
Só para quem vai compilar o programa: é necessário Python 3.10+ e as dependências customtkinter, pyodbc, pandas, pillow, openpyxl, pyinstaller, pytest (o BUILD.bat instala tudo, inclusive o próprio Python), além do Inno Setup 6 para gerar o instalador. Quem apenas usa o sistema não precisa de nada disso.
03 — Instalação

Instalação pelo Instalador

O Max_Importa é distribuído como um instalador único — MaxImporta_Setup_4.1.1.exe — que já traz o programa, a documentação, os modelos de importação, o banco ZERO e os pré-requisitos. Não é preciso instalar Python nem compilar nada.

1
Executar como Administrador
Clique com o botão direito em MaxImporta_Setup_4.1.1.exe → Executar como administrador. A elevação é necessária porque o instalador pode precisar instalar o driver ODBC e o Visual C++ no sistema.
2
Pasta de instalação
O padrão é C:\Max\MaxImporta — e não "Arquivos de Programas" de propósito: o sistema grava o max_importa.ini e a pasta Log\ ao lado do executável, e o Windows não permite escrita em Program Files para usuários comuns. A pasta é criada já com permissão de escrita para o grupo Usuários.
3
Pré-requisitos automáticos
O instalador verifica e instala somente se faltarem: o Microsoft ODBC Driver 17 for SQL Server (obrigatório para conectar) e o Visual C++ Redistributable x64 (dependência do ODBC). Ambos são instalados em modo silencioso. Se já existirem na máquina, nem são copiados — poupando tempo e espaço.
4
O que é instalado
Além do Max_Importa.exe: esta documentação e o histórico de versões (HTML), a subpasta Modelos\ com a planilha e os arquivos-modelo de importação, e a subpasta BD_ZERO\ com o banco "zero" compactado (destino para migração e testes).
5
Atalhos criados
No menu Iniciar, o grupo Max Importa recebe: o programa, a Documentação (HTML), o Histórico de Versões, o LEIA-ME, a Pasta do Banco ZERO e o desinstalador. O atalho na área de trabalho é opcional — marque a caixa durante a instalação se quiser.
6
Primeiro uso — pasta de logs
A pasta C:\Max\MaxImporta\Log\ já é criada pelo instalador. É nela que ficam os logs, os relatórios (.txt, .html, .json) e os arquivos de erro. O caminho é salvo em max_importa.ini e pode ser alterado no menu principal a qualquer momento.
🔄
Atualizar de uma versão anterior: basta executar o instalador da versão nova por cima da instalação existente — não é preciso desinstalar antes. O instalador mantém um identificador de produto fixo, então o Windows reconhece a atualização e substitui os arquivos. Suas configurações (max_importa.ini), perfis de mapeamento (max_importa_perfis.json) e a pasta Log\ são preservados.
🔌
Se o ODBC não instalar: ao final, o instalador confere se o ODBC Driver 17 for SQL Server ficou realmente presente. Se não estiver (por exemplo, se o Visual C++ falhou), ele avisa na tela e indica o download manual em https://aka.ms/odbc17. Sem esse driver o programa abre, mas não conecta ao SQL Server.
🗑️
Desinstalação: pelo atalho Desinstalar Max Importa no menu Iniciar, ou por Configurações → Aplicativos do Windows. Os pré-requisitos (ODBC e Visual C++) não são removidos, por serem componentes de sistema que outros programas podem usar.
🛠️
Para desenvolvedores — gerar o instalador: o executável é compilado com python -m PyInstaller max_importa.spec --noconfirm --clean (ou pelo BUILD.bat, que roda os testes como gate antes de compilar) e o instalador é gerado no Inno Setup 6 com ISCC.exe MaxImporta_Setup.iss. O passo a passo completo está em docs/BUILD.md.

06 — Configuração de Logs

Pasta de Logs e Relatórios

O Max_Importa salva todos os arquivos de log e relatório em uma pasta configurável pelo usuário, persistida no arquivo max_importa.ini.

⚙ Diálogo: Configurar pasta de logs
Acessível pelo botão "⚙ Configurar pasta de logs" no menu principal. Exibe o caminho atual e permite:

• Campo de texto editável com o caminho completo da pasta
• Botão 📂 para navegar e selecionar a pasta pelo explorador
• Botão "✔ Salvar" — grava em max_importa.ini e cria a pasta imediatamente se não existir
• Botão "↺ Restaurar caminho padrão" — restaura para C:\Max\MaxImporta\Log\
Estrutura do max_importa.ini
[Paths] log_dir = C:\Max\MaxImporta\Log
  • 📁
    Pasta padrão: C:\Max\MaxImporta\Log\ — criada automaticamente na primeira execução se não existir.
  • 📄
    max_importa.ini: salvo na mesma pasta do executável. Se apagado, a pasta padrão é usada na próxima execução e o arquivo é recriado ao salvar.
  • 🔒
    Independência por janela: cada janela de importação aberta cria seu próprio logger isolado — múltiplas janelas abertas na mesma sessão não interferem nos arquivos de log umas das outras.
07 — Mapeamento

Como Funciona o Mapeamento de Campos

Após selecionar o arquivo, o sistema detecta automaticamente as colunas e tenta mapear por nome idêntico. Corrija o que for necessário antes de importar.

1
Selecionar o arquivo
Clique em "📂 Selecionar CSV / TXT". O sistema aceita arquivos separados por tabulação, ponto-e-vírgula ou vírgula — o separador é detectado automaticamente pela primeira linha do arquivo.
2
Auto-mapeamento
Colunas do arquivo com o mesmo nome do campo do banco são mapeadas automaticamente. As demais ficam como [ ignorar ] para seleção manual.
3
Ajuste manual no grid
O grid exibe todos os campos com fundo alternado (claro/padrão) nos campos opcionais para facilitar a leitura. Campos OBRIGATÓRIO têm fundo rosa, o campo CHAVE tem fundo amarelo claro. Para cada campo, selecione a coluna correspondente no combobox.
4
Validação pré-importação
Ao clicar em "🚀 INICIAR IMPORTAÇÃO", o sistema valida os campos obrigatórios antes de iniciar. No INSERT, qualquer valor vazio, NULL, NONE ou NAN em campo obrigatório bloqueia a importação e exibe as linhas com problema. No UPDATE (desde a v4.0.2) só a chave é exigida — o registro já existe no banco; os demais campos são opcionais.
🟡
CHAVE
Campo de identificação primária (proId / cliId). Regras especiais de validação e geração automática por IDENTITY.
🔴
OBRIGATÓRIO
Deve ser mapeado e preenchido em todas as linhas. Importação bloqueada se houver valor vazio ou NULL.
🟣
LOOKUP
Consultado em tabela auxiliar (ex: produtoUn, proNCM). O valor precisa existir no banco de dados.
⚫
OPCIONAL
Pode ficar em [ ignorar ]. No INSERT, grava NULL quando não informado ou vazio. No UPDATE, célula vazia mantém o valor que está no banco.
🛡️
No UPDATE, célula vazia NÃO apaga (v4.0.2): se uma coluna está mapeada mas a célula daquela linha está em branco, o campo é deixado de fora da atualização e o valor que já está no banco é preservado. Antes, o branco era gravado por cima — apagava e-mail, endereço e afins, e nos campos de preço chegava a zerar venda e custo. A regra vale por linha: a mesma coluna pode atualizar uma linha e ser ignorada na seguinte. Não é possível limpar um campo pelo arquivo — para isso, use o Manager.
🔑
No UPDATE só a chave é obrigatória (v4.0.2): em Produtos, o proId; em Clientes, o cliId (ou o cliCpfCgc, quando o cliId não vem no arquivo). Todo o resto é opcional — dá para atualizar só o preço de um produto sem precisar mapear descrição, CST, código, unidade e NCM. Continua sendo necessário mapear ao menos um campo além da chave, senão não há o que atualizar. Nessa operação a tela não mostra o selo FALTA e o contador passa a considerar apenas a chave.
🏬
Banco com mais de uma loja (v4.1.0): se a tabela config tiver mais de uma empresa, o sistema abre uma janela perguntando em quais lojas a importação vale — antes de começar. Em banco de uma loja nada é perguntado e o comportamento é o de sempre.

A marcação quer dizer coisas diferentes conforme a operação, e a própria janela avisa qual: no INSERT ela define onde o registro vai aparecer — os dados são gravados em todas as empresas (uma linha por loja) e a marcação vira a visibilidade; no UPDATE ela define em quais lojas os dados mudam, e a visibilidade já configurada não é alterada (ela pode ter sido ajustada no Manager).
💰
Financeiro em multi-loja: cada título pertence a uma loja, então ele não é replicado. Use o campo novo empId no arquivo para dizer a loja de cada linha — é opcional, e sem ele o título vai para a empresa 1. Se o banco tiver várias lojas e o campo não estiver mapeado, o sistema avisa antes de gravar. Um empId que não existe no cadastro de empresas não é gravado: a linha é pulada e aparece no arquivo de erros.
🛑
CPF/CNPJ repetido não é atualizado (v4.1.1): no UPDATE por documento, se o CPF/CNPJ do arquivo aparecer em mais de um cliente, a linha é pulada — nenhum cadastro é alterado. Antes, o sistema escolhia um deles ao acaso e gravava por cima, sobrescrevendo o cliente errado. Documento repetido é comum: há bases com o mesmo CNPJ em 19 clientes. Para atualizar mesmo assim, resolva a duplicidade no Manager ou use o cliId como chave.
🧾
O que não foi atualizado agora tem arquivo (v4.1.1): linhas cujo proId/cliId não existe no banco, ou com documento ambíguo, saem em NAO_ATUALIZADOS_<MÓDULO>_<data>.csv com o motivo. O resumo passou a ter um contador "não encontrados" próprio: antes, uma chave inexistente contava como "atualizado" e um arquivo inteiro com IDs errados terminava dizendo que tudo tinha entrado.
🏷 Badge de Operação
Cada janela de importação exibe no cabeçalho um badge colorido indicando a operação selecionada no menu:

► INSERIR   vermelho — operação INSERT
◄ ATUALIZAR   cinza — operação UPDATE

O badge não pode ser alterado dentro da janela. Para trocar a operação, volte ao menu e escolha o botão correspondente.

⚠️
Regras do proId — INSERT:
• proId vazio / em branco: segue a numeração do próprio banco (coluna IDENTITY). O ID gerado é capturado via SCOPE_IDENTITY() e vinculado a produto_empresa e codBarras. Ideal para migração — não é preciso inventar IDs.
• proId informado: insere o ID explicitamente (SET IDENTITY_INSERT) e verifica colisão.
• Ao final de qualquer INSERT: o seed do IDENTITY é reconfigurado para MAX(proId) + 1 automaticamente.
🆕
Unidade não encontrada em produtoUn — cadastro automático: se a unidade (proUn) não existir, o sistema a cadastra automaticamente em produtoUn (unpUn = código, unpDescricao = código, unpDesativar = 0) e já vincula proUnComercialId, proUnTrib e proUnTribId ao produto. Ao final, exibe a lista das unidades criadas automaticamente para conferência.
✂️
Corte automático de tamanho (evita erro "dados seriam truncados"): textos maiores que a coluna do banco são cortados automaticamente no limite — proDescricao (100), proLocalizador (20), proPrateleira (20), proCodigo (50), proUn (10), proCodCSOSN (3), proCodCst2 (2), proTipo (1).

🧩
Campos AUTO/OPCIONAL — tratamento interativo ao iniciar: ao clicar em INSERIR, se estes campos estiverem vazios o sistema pergunta como proceder (e preenche conforme a resposta), em vez de bloquear a importação:

• Nome Fantasia: se o documento for CPF → fica em branco automático; se for CNPJ → pergunta se deseja repetir o Nome. Aviso: repetir o Nome no Fantasia (ou quando o cliente já possui Fantasia) pode gerar problemas na emissão de documentos fiscais — conferir após a importação.
• RG / Inscrição: se CPF → branco automático; se CNPJ → pergunta se preenche com ISENTO.
• Número do endereço: pergunta se preenche com S/N ou deixa vazio.

Os demais campos (CPF/CNPJ, Nome, Endereço, Bairro, Cidade, IBGE, UF, CEP) permanecem obrigatórios.
🚫
IDs reservados pelo sistema: cliId de 1 a 10 são reservados pelo MaxManager. Qualquer linha com esses valores é rejeitada antes de iniciar a importação, sem contato com o banco.
💡
INSERT — Lógica do cliId:
• Com cliId no arquivo → verifica colisões. IDs já existentes são pulados automaticamente (não causam erro, contabilizados como "pulados").
• Sem cliId → IDENTITY automático a partir de 11.

• Com cliId mapeado → atualiza diretamente pela chave primária.
• Sem cliId → sistema pergunta antes de iniciar se deseja usar CPF/CNPJ como chave de localização.

👥
Clientes — modo "banco zero" (APAGA o destino)
Cópia idêntica
  • ⚠️
    Ciência do usuário: antes de iniciar, um diálogo avisa que as tabelas cliente e cliente_empresa do DESTINO serão APAGADAS e recomenda usar um banco ZERADO. Só continua com a confirmação.
  • 🧹
    Limpeza segura: DELETE em transação — se o destino tiver dados relacionados (vendas, caixa, etc., há ~150 tabelas com FK para cliente), a limpeza é bloqueada e nada é apagado.
  • 🔢
    Reset dos contadores: DBCC CHECKIDENT ('cliente', RESEED, 0) e idem em cliente_empresa — a numeração volta a começar do 1.
  • 📋
    Cópia idêntica: TODOS os cliId (inclusive 1–10) são mantidos, sem validação de obrigatórios e sem a regra de IDs reservados. Campos: cliCpfCgc, DataInclusao, cliDesativa, cliEmail, cliFantasia, cliFatBairro, cliFatCep, cliFatCidade, cliFatCidCodIBGE, cliFatEnd, cliFatEndNumero, cliFatUf, cliFone, cliId, cliNome, cliRgInsc, cliTipoCad, cliTipo. O vínculo cliente_empresa é recriado.
  • 👯
    Duplicados (cliNome + cliCpfCgc iguais): o sistema informa quantos se repetem e pergunta se deseja desativar os repetidos — mantém ATIVO apenas o mais novo (maior cliId) e coloca cliDesativa = -1 nos demais — ou manter todos como na origem.
🔐
Permissões de Usuário (UsuarioPermissao)
  • 📄
    Copia uspUsuId + uspObjeto; o uspId é gerado pelo destino.
  • ⏭️
    Pula permissões que já existem no destino (mesmo usuário + objeto).
  • 🛡️
    Ignora sem erro permissões cujo usuário (cliId) não existe no destino (FK uspUsuId → cliente.cliId) — por isso Clientes migram antes.
📦
Produtos — com tratamento de estoque e acerto automático
  • 🔑
    Mantém o proId da origem; produtos já existentes no destino não são duplicados (IF NOT EXISTS).
  • ⚙️
    Aplica as mesmas regras do importador: unidade cadastrada automaticamente em produtoUn, auto-criação de fabricante/grupo/subgrupo/classe, corte de textos longos, código de barras.
  • ❓
    Pergunta ao iniciar: "Deseja migrar o ESTOQUE ATUAL?"
    • Não → todos os produtos entram com proEstoqueAtual = 0 no destino.
    • Sim → se houver produtos com estoque negativo na origem, pergunta se deseja iniciá-los com ZERO (Sim = zera só os negativos | Não = mantém os valores da origem).
  • 📦
    Acerto de estoque pós-migração: ao concluir, se houver produtos com estoque > 0 no destino, é gerado automaticamente um ACERTO DE ESTOQUE PENDENTE (status 'A', obs "MAXDATA SISTEMA - MIGRACAO", usuário admin cliUsuLoginId = 2) e o sistema avisa: rode o acerto no Manager para efetivar o estoque.
💰
Financeiro (vendaPgto)
  • 🔎
    Localiza o cliente no destino pelo CPF/CNPJ; não encontrado → linha pulada (contada como "não encontrados").
  • 🆔
    O pgtId é gerado novo no destino (não mantém o da origem).
  • 🔁
    Idempotente: antes de inserir, verifica se já existe um lançamento igual no destino (empId + pgtClienteId + pgtValor + pgtData + pgtVecmto + pgtNumDoc + pgtTipoConta) e pula se existir. Rodar a migração 2× não duplica os lançamentos.
🧬
Resiliente a schemas diferentes: os SELECTs na origem são montados dinamicamente, detectando quais colunas existem no banco de origem. Colunas ausentes viram NULL em vez de quebrar — funciona entre versões/schemas diferentes do MaxData.
📊
Totais consolidados + relatório: ao final, a tela mostra os totais de todas as opções migradas juntos (inseridos / não inseridos / erros) e um relatório próprio RELATORIO_MIGRACAO_AAAAMMDD_HHMM.txt é sempre salvo na pasta de logs — inclusive quando ocorre erro.
🧾
Conferência ORIGEM × DESTINO (reconciliação): após migrar, o sistema compara automaticamente origem e destino — contagens de cliente, UsuarioPermissao, produto, codBarras e vendaPgto, além das somas de estoque (proEstoqueAtual) e de valores do financeiro (pgtValor). Cada linha sai com status ✅ confere, ℹ️ diferença esperada (ex.: estoque zerado por opção) ou ⚠️ divergente com a possível causa — na tela, no log e no relatório.
🚫
Antes de migrar: faça BACKUP do banco de destino. Origem e destino precisam estar na mesma instância SQL (a conectada no login). Para Clientes, use preferencialmente um banco de destino zerado.
12 — Segurança e Qualidade

Recursos de Proteção e Qualidade dos Dados

Recursos acrescentados entre as versões 3.2 e 3.8, voltados a não perder dado em silêncio e a evitar surpresa em produção. O histórico completo está em Histórico de versões.

🔎
Simulação (dry-run)
Nas três telas de importação (inclusive nos modos de atualização), a caixa "Simular (não grava)" percorre o arquivo inteiro — lookup, conversão e validações — e informa o que aconteceria, sem gravar nada no banco. Também não gera acerto de estoque nem renomeia o arquivo, então dá para conferir e rodar de verdade em seguida. O resumo lista os comandos que seriam executados, por tabela.
🔍
Pré-flight de schema
Na Migração, o botão "Verificar compatibilidade" compara origem × destino somente leitura: tabelas e colunas ausentes, tipo, tamanho, precisão, collation e NOT NULL. Quando a coluna do destino é menor, conta quantas linhas realmente estourariam. Também roda automaticamente ao iniciar a migração — se houver bloqueante, pede confirmação.
✔️
Regras de negócio
Durante a importação são conferidos CPF/CNPJ (dígito verificador), formato de e-mail, faixa de datas e valores negativos. Os avisos não bloqueiam o registro, mas aparecem no log e no resumo. Um documento inválido nunca casa no lookup — o aviso explica o "CPF/CNPJ não encontrado".
👥
Dedupe de clientes
Ao importar Clientes, o sistema aponta duplicados prováveis — comparando documento, nome idêntico e nome parecido, e ignorando documentos "preenchedores" como 00000000000, que não identificam ninguém. Nunca funde registros: juntar clientes é irreversível, então a decisão fica com quem conhece a base. A lista sai no log, no relatório HTML e num DUPLICADOS_CLIENTES_*.csv.
📋
Perfis de mapeamento
O mapeamento de colunas pode ser salvo com nome e reaplicado em importações futuras (por módulo). Ao aplicar, o sistema confronta o perfil com as colunas do arquivo e avisa quais sumiram, se o layout mudou. Guardado em max_importa_perfis.json.
🛡️
Backup, retry e integridade
O backup do destino é obrigatório quando Clientes está no plano (única etapa que apaga dados). Erros transientes (deadlock, timeout, queda de conexão) re-tentam com backoff; erro de dado sobe na hora. Ao fim, a reconciliação verifica FKs desabilitadas e linhas órfãs.
🔐
Credenciais e auditoria
A senha não fica embutida no programa: há autenticação SQL ou Windows, e "lembrar credenciais" grava a senha criptografada via DPAPI (só nesta máquina/usuário). Cada migração registra uma linha por entidade em MaxImporta_Auditoria no destino.
ℹ️
Cancelamento e progresso: toda operação longa mostra o progresso por registro ("X de Y — NN%") e pode ser cancelada. Os importadores param entre linhas; a migração para entre entidades (ponto seguro — a entidade em curso termina inteira).
13 — Formatos de Arquivo

Formatos de Arquivo Aceitos

O sistema aceita planilhas .xlsx e arquivos de texto .txt / .csv, com detecção automática de separador e de encoding (desde a v3.7.0).

  • 📄
    Extensões: .xlsx, .xlsm, .csv e .txt. Planilhas do Excel são lidas direto — não é mais preciso exportar para texto antes.
  • 📐
    Separadores (detectados automaticamente): Tabulação (TAB) — prioridade; Ponto-e-vírgula (;); Vírgula (,). Não se aplica a .xlsx.
  • 🔤
    Encoding (detectado automaticamente): BOM (UTF-8/UTF-16) → UTF-8 estrito → CP1252 (Windows-BR) como último recurso. Antes da v3.7.0 era fixo em Latin-1, o que corrompia acentos de arquivos UTF-8.
  • 1️⃣
    Primeira linha: deve conter o cabeçalho com os nomes das colunas. As demais linhas são dados.
  • 🔢
    Decimais: aceitos com vírgula (1.234,56) ou ponto (1234.56) como separador. O sistema normaliza automaticamente antes de gravar.
  • 📅
    Datas aceitas: ISO (AAAA-MM-DD, com ou sem hora e milissegundos), BR com barra (DD/MM/AAAA), traço (DD-MM-AAAA), ponto (DD.MM.AAAA), ISO com barra (AAAA/MM/DD), ano de 2 dígitos e serial do Excel. Um valor de data não reconhecido não é mais descartado em silêncio: aparece no log e no resumo.
  • ✔️
    Situação do título (pgtPago): o MaxManager espera S = Concluído e N = Aberto. Sinônimos comuns (C, SIM, PAGO, QUITADO, 1 / A, ABERTO, 0) são normalizados automaticamente.
ℹ️
Valores nulos: células vazias e os textos NULL, NONE e NAN (maiúsculos ou minúsculos) são todos interpretados como NULL e não causam erro em campos opcionais.
14 — Logs e Relatórios

Logs e Relatórios de Importação

Cada importação gera vários arquivos na pasta configurada em max_importa.ini (padrão: C:\Max\MaxImporta\Log). Os loggers são independentes por janela — múltiplas sessões simultâneas não interferem entre si.

🌐
Relatório HTML (v4.0.0): além do .txt e do .json, cada importação gera um RELATORIO_<OPERAÇÃO>_<data>.html — com cartões de totais, barras proporcionais, a seção Qualidade dos dados (documentos inválidos, datas não reconhecidas, pgtPago normalizado), a tabela de CPF/CNPJ não encontrados e o log completo. É autocontido: abre offline com duplo clique, sem internet.
🧾
Saída estruturada (v3.4.0): RESULTADO_*.json traz o resumo da operação (versão, banco, contagens, erros) para integração, e ERROS_*.csv lista as falhas já no formato que o Excel abre.
📋
Arquivo de Log (.log)
Registro em tempo real de cada operação. Atualizado linha a linha durante a importação.

LOG_MAX_IMPORTA_AAAAMMDD_HHMM.log
LOG_MAX_IMPORTA_CLI_AAAAMMDD_HHMM.log
LOG_MAX_IMPORTA_FIN_AAAAMMDD_HHMM.log
📊
Relatório Final (.txt)
Resumo completo com todos os eventos, contadores de sucesso, erros e pulados. Gerado ao término da importação (e também quando a validação falha).

RELATORIO_MAX_IMPORTA_AAAAMMDD_HHMM.txt
RELATORIO_MAX_IMPORTA_CLI_...txt
RELATORIO_MAX_IMPORTA_FIN_...txt
❌
Arquivo de Erros (.txt)
Gerado quando há erros/itens inválidos, listando os NOMES dos itens/clientes que falharam (ou os campos vazios, na falha de validação).

📦
Após a importação (evita duplicidade): ao concluir (com ou sem erros), o programa renomeia o arquivo importado com o status e data/hora — ex.: clientes_IMPORTADO_OK_AAAAMMDD_HHMMSS.txt ou produtos_IMPORTADO_COM_ERROS_...txt — e limpa a seleção na tela, impedindo que o mesmo arquivo seja importado duas vezes por engano. 15 — Solução de Problemas

Erros Comuns e Soluções

Lista dos erros mais frequentes com orientação de resolução.

Erro / SituaçãoCausaSolução
Violação de PRIMARY KEY ID já existe na tabela — tentativa anterior gravou parcialmente Use UPDATE para os registros já existentes, ou exclua-os antes de reimportar
Nome de coluna inválido 'xxx' Campo mapeado não existe na tabela de destino Verifique o nome exato do campo na documentação e corrija o mapeamento
Dados de cadeia seriam truncados Campo de texto excede o limite da coluna no banco Resolvido: o sistema corta automaticamente no limite da coluna, tanto em clientes quanto em produtos (proDescricao 100, proLocalizador 20, etc.)
No module named 'PIL' (ao compilar) .exe antigo, gerado sem o Pillow empacotado Resolvido: o BUILD.bat instala o pillow e o .spec inclui PIL nos hiddenimports. Basta regerar o .exe.

0 inseridos / "proId vazio, ignorando" (produtos) Arquivo de migração sem a coluna proId preenchida Resolvido: proId vazio agora segue a numeração do próprio banco (IDENTITY). Não é preciso preencher proId.

Correções da v4.1.1: o UPDATE por CPF/CNPJ não sobrescreve mais o cadastro errado quando o documento está repetido no banco — a linha é pulada e reportada · o resumo parou de contar como "atualizado" a linha cujo ID não existe, e essas linhas saem num arquivo próprio com o motivo.

Novidades da v4.1.0: suporte a banco com mais de uma loja — nova janela para escolher em quais empresas a importação vale, os cadastros passam a nascer em todas as lojas com a visibilidade definida pela marcação, o Financeiro ganhou o campo empId para indicar a loja de cada título, e a migração pergunta as empresas no assistente.

Correções e novidades da v4.0.2: o UPDATE não apaga mais dados — célula vazia no arquivo passou a significar "não mexer neste campo", em vez de gravar vazio por cima (nos campos de preço chegava a zerar venda e custo) · no UPDATE só a chave é obrigatória (proId / cliId), os demais campos ficaram opcionais · novo campo proCodCst1 (origem da mercadoria, 0 a 9), que completa o CST junto com o proCodCst2 · a área de mapeamento voltou a ocupar a tela — uma barra decorativa do log estava consumindo metade da altura, deixando só 4 linhas visíveis.

Correções da v4.0.1: importar base grande (55 mil clientes) não trava mais — o detector de duplicados passou a ser limitado (achados agrupados em resumo, sem explodir a memória) · os botões de ação ficam sempre visíveis em telas menores (1366×768) · o INSERT de Clientes e Produtos ficou ~4× mais rápido (comando único por linha, ganho maior sobre a rede).

Novidades da v4.0.0: pré-flight de compatibilidade de schema antes de migrar (com truncamento medido, não estimado) · validação de CPF/CNPJ, e-mail, faixas de data e valores no momento da importação · relatório HTML de fechamento com a seção de qualidade dos dados · perfis de mapeamento salvos por layout de arquivo · correção do pgtPago (o MaxManager espera S = Concluído / N = Aberto).

Antes disso: importação de planilhas .xlsx, detecção automática de encoding e simulação (dry-run) na v3.7.0 · reconciliação com validação de conteúdo, integridade referencial, backup obrigatório e retry na série 3.6.
