========================================================
 MAX_IMPORTA — HISTÓRICO DE VERSÕES (CHANGELOG)
========================================================

Formato da versão: MAJOR.MINOR.PATCH
  MAJOR = mudança grande / incompatível
  MINOR = novos recursos compatíveis
  PATCH = correções

A versão fica definida em max_importa.py -> APP_VERSION
e aparece na tela de login, nos títulos das janelas e no
cabeçalho dos relatórios.

--------------------------------------------------------
 [2.1.0] - 2026-07-01  (BASELINE antes da próxima grande alteração)
--------------------------------------------------------
Este é o marco estável atual. A partir daqui será feita
uma alteração grande (que deverá virar a 3.0.0).

PRODUTOS
- proId vazio agora segue a numeração do próprio banco
  (IDENTITY), capturada via SCOPE_IDENTITY e vinculada a
  produto_empresa e codBarras. (Migração sem inventar IDs.)
- Unidade (proUn) inexistente é cadastrada automaticamente
  em produtoUn e já vinculada ao produto.
- Corte automático de textos longos no limite da coluna
  (fim do erro "dados seriam truncados"): proDescricao 100,
  proLocalizador 20, proPrateleira 20, proCodigo 50,
  proUn 10, proCodCSOSN 3, proCodCst2 2, proTipo 1.

CLIENTES
- Novo campo cliTipo no INSERT e UPDATE de clientes
  (0 = Pessoa Física, 1 = Pessoa Jurídica). Incluído também na
  migração entre bancos e nos modelos (txt e xlsx).
  * Quando cliTipo não é mapeado (ou vem vazio), é DERIVADO
    automaticamente do cliCpfCgc: CPF (11 díg) = 0, CNPJ (14 díg)
    = 1. CPF/CNPJ vazio deixa cliTipo vazio.
- Campos Fantasia, RG/Inscrição e Número do endereço deixaram
  de bloquear a validação: tratamento interativo ao iniciar.
    * Fantasia vazio: CPF -> branco automático;
      CNPJ -> pergunta se repete o Nome (aviso de risco em
      documentos fiscais, conferir após importar).
    * RG/Insc vazio: CPF -> branco automático;
      CNPJ -> pergunta ISENTO ou branco.
    * Número vazio: pergunta S/N ou vazio.
- Demais campos permanecem obrigatórios (CPF/CNPJ, Nome,
  Endereço, Bairro, Cidade, IBGE, UF, CEP).

MENSAGENS / LOGS
- Mensagens de erro de obrigatórios AMIGÁVEIS (nome do campo,
  quantidade e linhas), iguais nos 3 importadores.
- Relatório e arquivo de ERROS gerados também quando a
  validação falha (antes não gerava nada).
- Ao concluir (com ou sem erros): o arquivo importado é
  renomeado com status + data/hora (..._IMPORTADO_OK_... /
  ..._IMPORTADO_COM_ERROS_...) e a seleção da tela é limpa,
  evitando reimportar o mesmo arquivo por engano.
- Arquivo ERROS_*.txt lista os nomes dos itens/clientes que
  falharam.

BUILD / EMPACOTAMENTO
- BUILD.bat instala o Python automaticamente se ausente
  (winget ou instalador oficial) e se reabre para aplicar PATH.
- BUILD.bat se reabre sem privilégios quando aberto como
  Administrador (PyInstaller não roda elevado).
- Pillow empacotado no .exe (fim do erro "No module named PIL");
  PIL incluído no hiddenimports do .spec.

 [3.0.0] - 2026-07-01  (alteração grande)
--------------------------------------------------------
NOVO MÓDULO — MIGRAÇÃO ENTRE BANCOS MAXDATA (banco -> banco)
- Botão no menu principal: "Migração entre Bancos MaxData".
- Copia dados diretamente de um banco para outro da MESMA
  instância SQL, sem precisar de arquivo.
- O usuário escolhe o banco de ORIGEM e o de DESTINO (lista
  dos bancos ONLINE da instância).
- Escolhe o que migrar: Clientes, Produtos e/ou Financeiro.
- Reutiliza a lógica de INSERT dos importadores (unidade
  automática em produtoUn, corte de tamanho de textos, etc.).
- Mantém os IDs de origem (proId/cliId); registros que já
  existirem no destino são pulados (sem erro).
- Ordem automática: Clientes -> Produtos -> Financeiro
  (financeiro localiza o cliente por CPF/CNPJ no destino).
- Gera os mesmos relatórios (RELATORIO_*.txt) por entidade.

COMO FUNCIONA (técnico)
- SELECT na origem já produz colunas com o nome dos campos
  que os importadores esperam (mapping identidade).
- O ID gerado/mantido segue as mesmas regras dos INSERTs.

MIGRAÇÃO — RESILIÊNCIA A SCHEMA E RELATÓRIO
- Os SELECTs de origem passaram a ser montados DINAMICAMENTE,
  detectando quais colunas existem no banco de origem. Colunas
  ausentes viram NULL — funciona entre versões/schemas diferentes
  do MaxData (corrige erros como 'cliDatCad'/'ncmCodigoNCM'
  inválido em bancos de schema diferente).
- A migração agora SEMPRE gera um relatório próprio
  (RELATORIO_MIGRACAO_AAAAMMDD_HHMM.txt), inclusive quando ocorre
  erro (antes, se o SELECT falhava, não gerava nenhum log).

MIGRAÇÃO — PERMISSÕES E TOTAIS
- Nova opção "Permissões de Usuário" na migração: copia a tabela
  UsuarioPermissao (uspUsuId, uspObjeto). Ordem: Clientes ->
  Permissões -> Produtos -> Financeiro.
    * Pula permissões que já existem (mesmo usuário + objeto).
    * Ignora (sem erro) permissões cujo usuário/cliId não existe
      no destino (FK uspUsuId -> cliente.cliId).
- Ao concluir a migração, a tela mostra os TOTAIS CONSOLIDADOS de
  cada opção migrada juntos (inseridos / não inseridos / erros),
  em vez de um resumo separado por entidade.

ACERTO DE ESTOQUE (produtos)
- Após importar/atualizar produtos com SUCESSO, o sistema
  verifica se há produtos com proEstoqueAtual > 0.
    * Se não houver: informa que não há estoque para acerto.
    * Se houver: habilita o botão "Gerar Acerto de Estoque".
- O botão cria um ACERTO DE ESTOQUE PENDENTE (status 'A') com
  todos os produtos com estoque > 0 (produtoAcertoEstoque +
  produtoAcertoEstoqueItem), para ser rodado no Manager.
- Usa o usuário admin (cliUsuLoginId = 2) e o empId do destino.

CORREÇÕES
- Tela de login redimensionada (altura) para o botão de
  confirmar banco aparecer corretamente.

ATENÇÃO
- Faça BACKUP do banco de destino antes de migrar.
- Origem e destino precisam estar na mesma instância SQL
  (a mesma conectada no login).

 [3.2.0] - 2026-07-04
--------------------------------------------------------
BOTÃO CANCELAR — interromper importação/migração com segurança
- Todas as janelas (Produtos, Clientes, Financeiro e Migração)
  ganharam um botão "⏹ Cancelar", habilitado apenas enquanto uma
  operação está em andamento.
- O cancelamento é COOPERATIVO e só ocorre em pontos SEGUROS:
    * IMPORTADORES (Produtos/Clientes/Financeiro): entre registros.
      Como o commit é feito por linha, os registros já gravados
      permanecem e nada fica pela metade; a operação para no próximo
      registro.
    * MIGRAÇÃO: entre ENTIDADES. A entidade em andamento é concluída
      inteira (mantendo o banco consistente, com as FKs reabilitadas)
      e as entidades restantes NÃO são executadas. Não interrompe no
      meio de uma entidade (onde há FKs desabilitadas, IDENTITY_INSERT
      e commits em lote), justamente para não deixar o destino num
      estado inconsistente.
- A migração cancelada mostra título/mensagem próprios ("Migração
  cancelada"), lista as entidades não migradas no log e só confere
  (reconciliação origem × destino) as entidades efetivamente migradas.
- O botão é reabilitado/rearmado automaticamente a cada nova operação.

 [3.2.1] - 2026-07-04
--------------------------------------------------------
SEGURANÇA — Credenciais de conexão
- A senha padrão NÃO fica mais embutida no binário. Antes o app
  trazia usuário E senha fixos no código (qualquer um que abrisse o
  .exe conseguia extrair a senha). Agora só o usuário padrão 'sa'
  (que não é segredo) é sugerido; a senha começa VAZIA e é digitada.
- Nova opção de AUTENTICAÇÃO no diálogo "Editar credenciais":
    * SQL Server (usuário + senha), ou
    * Windows (autenticação integrada — Trusted_Connection, sem senha).
  Em Windows auth, os campos de usuário/senha ficam desabilitados e
  nada sensível é armazenado.
- Novo "Lembrar credenciais nesta máquina": quando marcado, servidor,
  usuário e modo de auth são salvos no max_importa.ini e a SENHA é
  gravada CRIPTOGRAFADA via Windows DPAPI (CryptProtectData). O texto
  cifrado só pode ser decifrado pelo MESMO usuário do Windows na MESMA
  máquina — não fica em texto puro e não é portável para outra máquina.
    * Sem "lembrar", a seção [Conexao] do .ini é removida (não sobra
      nenhuma credencial em disco).
    * A criptografia usa a API nativa do Windows via ctypes — sem
      nenhuma dependência nova no build.
- A connection string passou a ser montada num único ponto
  (_montar_base_conn_str), conforme o modo de auth; login, menu e
  migração reaproveitam a mesma base (comportamento idêntico ao anterior
  para SQL auth).
